# Permissions and enforced tool access

- Status: accepted, amended by [decision 0067](0067-read-everywhere-and-write-inside-the-project.md) and for isolated hook execution by [decision 0065](0065-script-hooks-and-the-add-on-contract.md), with remaining implementation work in `docs/roadmap.md`
- Date: 2026-11-06

## Context

The initial boundary allows project access by default and asks for outside paths and the network. Decision 0067 replaces it with reads everywhere except denied paths, project writes, and approval for outside writes and network access. A command's text cannot establish which resources its program or descendants access. Pi supplies tool execution, cancellation, and custom session entries, but no operating system boundary or browser approval lifecycle.

Profiles now own agent settings under decision 0061. A project profile is writable project content. A command must not change the configuration that widens its own authority without approval. Linux bubblewrap can mask denied files and report successful empty reads, which would give the model false facts.

## Decision

- Permission policy belongs to the selected profile under `settings.permissions`. Its version is 2 after the migration of decision 0067. The default mode is `project`, the environment is `minimal`, and rules and saved approvals start empty. Invalid policy blocks new work through the strict profile store.
- Path and network rules allow, ask, or deny. Deny precedes ask, and ask precedes allow. A read denial also prevents writes. Rules never infer authority from command prefixes.
- Project mode uses the concrete MXC ProcessContainer, Seatbelt, or bubblewrap backend. Windows requires BaseContainer. The stable V1 API disables telemetry on every operation. No weaker or unrestricted fallback runs.
- System roots are readable without startup approval under decision 0067. The runtime hash includes the package version, executable identity, system read roots, environment policy and names, and platform support facts. Changed facts invalidate pending operations.
- Shell keeps its original command string and shell arguments. Sandboxed Windows commands use PowerShell from its installer or Windows PowerShell 5.1. Git Bash and Store aliases cannot run in this boundary. Unrestricted mode retains the shell choices of decision 0035. Project discovery never runs a version query with host authority. The model sees when a version is not queried.
- Commands receive the published minimal environment name allowlist by default. Explicit profile variables apply afterward. The access token is removed last. Inheriting everything is an explicit profile choice. File workers receive a minimal environment without profile variables.
- Read, Write, and Edit run their existing implementations in restricted workers. The parent keeps Pi's mutation queue and supplies only the operation, model capabilities, model texts, limits, and file fingerprints. File contents are not read to construct an approval preview.
- Canonical paths and existing ancestor identities determine requested grants. A new file can require a broader parent grant, which the approval shows. File tools refuse known hard links and unresolved identities. The sandbox remains the boundary against link races.
- Independum's state directory is denied to project commands and file tools. Protected project configuration includes project `.independum`. Writes require approval even when an allow rule matches. Shell keeps the overlapping configuration read-only inside its writable project grant. It creates the project configuration directory before policy compilation so the read-only mount exists. An approved explicit write grant can open its exact requested path.
- Unsupported policy combinations refuse before execution. Bubblewrap masks existing denied folders, and the editable permission fact names them and explains that their empty view is not real content. Decision 0067 permits these private masks and describes their temporary writes in the editable permission fact. Denied files still refuse because masking can produce false content. Protected configuration uses nested read-only paths on every backend. Compilation of write-only rule exclusions remains unfinished and refuses explicitly.
- Approval stays inside the tool step. Its heading names the requested access in plain words, and the card shows only what the request asks for, with a Shell command as the step shows it. Exact resources and runtime facts unfold in disclosures. Choices run narrowest first and share one look, so none reads as the default. Path and network access offer Allow once, Allow for this chat, Always for this project, and Deny. A denied step reads Denied in the quiet tone, because the user chose it. Chat grants last until the server stops. Project grants save the exact access and resource identity in the profile for that project. Deny rules precede every grant. Waiting uses the ordinary quiet status. Execution time starts after authorization.
- Every saved approval appears in Permissions with a removal action. Removing it affects new operations. Persistent answers use conditional profile writes and recheck their binding inside the configuration lock. A save failure leaves the operation waiting. Approval records do not change the configuration binding that authorizes their own save, and other profile changes still invalidate pending decisions.
- Approval belongs to the server launch, chat, branch, tool call, copied validated input, resource identities, profile revision, and runtime hash. A changed binding invalidates it. The first valid answer wins, an identical answer is idempotent, and a conflicting or stale answer returns 409.
- Reply cancellation cancels pending decisions. Browser disconnection preserves them while the server runs. Restart grants no authority and replays no operations. Pi custom entries record waiting and terminal decisions without adding messages to model context.
- API messages default to headless approval delivery and return an unmet tool approval as `approvalRequired` immediately, even when a browser follows the chat. The UI explicitly selects browser approval delivery. Running commands keep their original authority after a profile change. New invocations revalidate the active profile.
- Unrestricted mode is a deliberate profile choice and requires an empty rule list. Choosing it asks for confirmation, and returning to project mode does not. It uses ordinary account authority. Permission facts have editable model texts and independent switches. Turning a fact off does not change enforcement.
- Session shows Permissions beside its configuration facts. Its detail uses the existing place sections and disclosures for mode, command environment, sandbox details, denied paths, saved approvals, rules, and protected project configuration. The saved profile file and exact engine facts unfold on demand. The existing profile file editor owns strict conditional policy saves.

## SDK evidence

The installed `@microsoft/mxc-sdk` version is 1.0.1. Its `dist/v1/types.d.ts` defines `readonlyPaths` as readable without write access. Its `dist/v1/container.js` passes both path lists unchanged to the native backend.

The packaged Linux `bin/x64/libmxc_ffi.so` contains `filesystem_resolve::resolve_path_plan`, and `bubblewrap::common::bwrap_command::build_args_classified_with_mode` calls it. The common plan orders parent mounts before child mounts. The builder uses `--bind` for writable paths and `--ro-bind` for read-only paths. A nested configuration path therefore overlays the writable project with its actual contents on a read-only mount. Denied folders instead use `--tmpfs` without a read-only remount. These mounts hide the host contents but allow private writes. V1 exposes only the cross-backend filesystem lists for bubblewrap. Its resolver chooses denial over an exact read-only grant, so listing a folder in both lists cannot make its mask read-only. Decision 0067 permits this policy because the host folder stays private and unchanged, and the editable permission fact describes the temporary writes. Denied files still refuse because their empty file masks can produce false content.

The same Linux command builder constructs `--tmpfs /tmp` before the classified path mounts. System read mounts now follow decision 0067. The native tests verify that outside host sentinels remain unchanged and new outside host files remain absent after both direct and detached child writes. Project writes must still appear on the host, and outside reads must succeed under decision 0067.

The packaged macOS `bin/arm64/libmxc_ffi.dylib` names the same shallow-to-deep read-only and read-write plan in its generated Seatbelt profile. Its read-only rule allows reads and denies `file-write*`. Windows uses native BaseContainer filesystem rules. The local request-aware `probe` accepts a writable parent and read-only child with `tier: "base-container"`, `needsDaclAugmentation: false`, and no warnings. No container starts during that probe.

The native regression test reads an existing sentinel, attempts to overwrite it, create a sibling, and rename the configuration directory, and then writes an ordinary project file. All protected writes must fail with errors while the original sentinel remains readable. Native execution still needs verification on supported hosts because this work environment cannot create a nested process security environment.

## Consequences

- This amends decisions 0029, 0035, 0036, 0041, 0042, 0044, 0045, 0048, 0054, and 0061.
- The implementation includes the adapter, Shell, file workers, explicit approval lifetimes and their API, profile policy, and Session inspection with revocation. A rule tester, dedicated rule editing routes, and the remaining native adversarial coverage stay on the roadmap.
- Default Shell policy uses a writable project and nested read-only configuration on Linux, macOS, and Windows. System read roots and the denied state directory follow decision 0067. Linux project tools run with the folder masks described by decision 0067. The raw SDK mask keeps host contents private and unchanged, but permits private writes inside the sandbox.
- Tool isolation does not isolate the server, Pi, or in-process add-ons. It does not recover secrets already supplied to a program, remove hard link aliases, roll back file changes, or protect a running development server that reloads writable harness code.
- Native tests use the real sandbox. Unsupported hosts and setup failures skip with their exact reason. Policy and lifecycle tests run without a real model or network service outside the test host.
